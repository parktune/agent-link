# Project: Codex-to-Codex Remote Agent Communication

## 1. 프로젝트 개요

서로 다른 물리적 또는 가상 서버에서 실행 중인 **독립적인 Codex CLI 대화 세션들이 인터넷을 통해 상호 통신하고, 작업을 위임하며, 실행 결과를 주고받을 수 있는 오픈소스 프로젝트**를 개발하고자 한다.

이 프로젝트의 핵심 목표는 Claude Code에서 Remote Control 및 관련 플러그인을 활용했던 경험을 Codex CLI 환경으로 확장하는 것이다.

단순히 원격 서버의 터미널을 조작하는 것이 아니라, 각 서버에 존재하는 Codex 에이전트가 독립적인 대화 컨텍스트와 실행 환경을 유지하면서 다른 에이전트와 협력하는 구조를 지향한다.

## 2. 목표 사용 시나리오

서버 A와 서버 B에는 각각 독립적인 Codex CLI 대화 세션이 실행 중이다.

- 서버 A: Codex Agent A
- 서버 B: Codex Agent B

사용자는 서버 B에서 Codex Agent B와 작업하고 있다.

작업 도중 서버 A에 저장된 데이터가 필요해지면 다음과 같이 지시한다.

> 서버 A에 있는 최신 데이터셋을 찾아서 현재 서버로 전송해 줘.

이후 다음 과정이 자동으로 수행되어야 한다.

1. Agent B가 서버 A의 Agent A에게 작업 요청을 전송한다.
2. Agent A는 요청을 자신의 대화 세션에서 수신한다.
3. Agent A는 서버 A의 로컬 환경을 조사하고 요청된 데이터를 찾는다.
4. Agent A는 필요한 파일을 서버 B로 전송한다.
5. 파일 전송 완료 및 무결성을 검증한다.
6. Agent A가 Agent B에게 작업 결과와 완료 상태를 반환한다.
7. Agent B는 해당 응답을 자신의 대화 컨텍스트에 반영하고 원래 작업을 계속 수행한다.

이 과정에서 사용자가 직접 SSH 접속, 파일 경로 검색, SCP 실행 등을 수행할 필요가 없어야 한다.

또한 요청과 응답은 양방향이어야 하며, Agent A도 Agent B에 작업을 요청할 수 있어야 한다.

## 3. 핵심 기술 가설

Codex CLI에는 다음과 같은 기능이 존재한다.

```bash
codex remote-control start
codex remote-control pair
```

실제로 Ubuntu 환경에서 `codex remote-control start`를 실행했을 때 다음 출력을 확인했다.

```text
Starting app-server daemon with remote control enabled...
This machine is available for remote control as taeyoonpc.
Daemon used app-server:
  path: /home/taeyoon/.codex/packages/app-server-daemon/current/bin/codex
  version: 0.166.0
```

이후 `codex remote-control pair`를 실행하면 8자리 페어링 코드가 발급된다.

여기서 다음과 같은 가설을 세운다.

**Codex가 제공하는 원격 제어 인프라를 활용하면, 공인 IP나 고정 Hostname을 사전에 교환하지 않고도 서로 다른 네트워크에 존재하는 Codex 에이전트 간 통신을 구현할 가능성이 있다.**

다만 아래 사항은 확인되지 않은 가설이므로 반드시 검증해야 한다.

- Pairing Code가 단순히 특정 공식 클라이언트를 등록하는 용도인지
- 외부 프로그램이 Pairing Code를 이용해 연결할 수 있는 공식 API가 있는지
- OpenAI의 중계 인프라가 임의의 Agent-to-Agent 메시지를 지원하는지
- 두 Codex CLI 인스턴스가 같은 계정으로 연결된 원격 머신을 조회하거나 선택할 수 있는지
- 원격 App Server에 접근할 수 있다면 기존 Codex 대화 세션에 메시지를 전달할 수 있는지
- 해당 기능이 안정적인 공개 인터페이스인지, 내부 구현에만 존재하는지

**중요: 페어링 코드가 존재한다는 사실만으로 임의의 CLI 간 접속이나 중계 API 사용이 가능하다고 가정하지 말 것.**

공식 문서, CLI help, 소스 코드 및 프로토콜 구현을 확인하고 실제로 검증 가능한 기능만 사용한다.

비공개 인증 체계를 우회하거나 내부 서비스의 미공개 API를 무단 사용하는 방식은 채택하지 않는다.

## 4. 필수 요구사항

### 4.1 독립적인 대화 세션 유지

서버 A와 B는 각자의 Codex 대화 세션을 유지해야 한다.

Agent B가 Agent A에 요청을 전달하더라도 Agent A의 기존 대화 컨텍스트가 사라지거나 별도의 무관한 에이전트로 대체되어서는 안 된다.

가능하다면 기존 TUI 세션의 thread ID를 이용해 요청을 전달한다.

Codex App Server의 thread 관리, turn 실행, 이벤트 구독 기능을 조사한다.

### 4.2 양방향 Agent-to-Agent 통신

다음 메시지 유형을 지원한다.

- `task_request`: 다른 에이전트에 작업 요청
- `task_accepted`: 요청 수락
- `task_progress`: 진행 상황 전달
- `task_completed`: 작업 완료
- `task_failed`: 작업 실패
- `file_transfer_request`: 파일 전송 요청
- `file_transfer_completed`: 파일 전송 완료
- `agent_message`: 일반적인 에이전트 간 메시지

모든 요청은 고유한 task ID를 가져야 하며, 요청 에이전트가 응답을 추적할 수 있어야 한다.

### 4.3 NAT 및 네트워크 독립성

가능하다면 다음 조건을 만족하도록 설계한다.

- 공인 고정 IP 불필요
- 포트 포워딩 불필요
- 사전에 상대 서버의 IP 주소를 알 필요 없음
- 서로 다른 NAT 환경에서도 통신 가능
- 서버 재시작 또는 재접속 이후에도 에이전트 식별 가능

OpenAI Remote Control 인프라를 공식적으로 활용할 수 없다면, 이를 대체할 수 있는 Relay Server, Tailscale 또는 다른 안전한 통신 계층을 검토한다.

특정 네트워크 백엔드에 강하게 종속되지 않도록 Transport Abstraction을 고려한다.

### 4.4 파일 전송

에이전트 간 메시지 전달과 실제 파일 전송을 분리한다.

파일 전송에는 다음 기능을 지원한다.

- 파일 및 디렉터리 전송
- 대용량 데이터 지원
- 전송 진행률
- SHA-256 기반 무결성 검증
- 실패 시 재시도 및 이어받기
- 명시적인 파일 접근 권한 관리

가능하다면 불필요하게 LLM 컨텍스트에 파일 내용을 포함하지 않고 직접 전송하도록 구현한다.

### 4.5 Codex CLI 통합

사용자가 자연어로 다른 에이전트에게 작업을 요청할 수 있어야 한다.

예시:

```text
서버 A의 Codex에게 최신 모델 체크포인트를 보내달라고 요청해.
```

MCP 또는 Codex가 공식적으로 제공하는 다른 확장 인터페이스를 활용한다.

최종적으로 사용자가 별도 통신 프로그램을 수동으로 조작하지 않아도, Codex가 필요한 통신 도구를 선택해 호출할 수 있어야 한다.

### 4.6 보안

- 에이전트 간 상호 인증
- 통신 암호화
- Pairing Code 및 인증 토큰의 안전한 보관
- 권한이 없는 에이전트의 접근 차단
- 요청별 실행 권한 제한
- 위험한 명령 및 파일 접근에 대한 승인
- 메시지 재전송 공격 방지
- 감사 로그

특히 원격 에이전트가 전달한 명령을 신뢰된 사용자 명령으로 취급하지 않도록 권한 경계를 분리한다.

## 5. 조사해야 할 기술

우선 다음 기능의 현재 구현과 공식 지원 여부를 확인한다.

1. Codex CLI Remote Control
2. Codex App Server 및 JSON-RPC 프로토콜
3. Codex thread 및 turn 관리
4. Codex CLI의 MCP 지원
5. Codex SDK
6. Codex CLI의 원격 연결 기능
7. Pairing Code 발급 및 검증 구조
8. 공식 OpenAI Relay 서비스의 외부 확장 가능성
9. A2A(Agent2Agent) 프로토콜 활용 가능성

GitHub의 Codex 오픈소스 저장소와 공식 개발자 문서를 우선적으로 참고한다.

버전별 기능 차이도 확인한다.

## 6. 개발 전략

다음 순서로 작업한다.

### Phase 1. 기술적 타당성 검증

아직 구현을 시작하기 전에 다음을 조사한다.

- 기존 Codex 세션에 외부에서 메시지를 전달할 수 있는가?
- 전달된 메시지로 실제 Codex 작업을 실행할 수 있는가?
- 실행 완료를 이벤트로 확인할 수 있는가?
- 다른 서버에서 해당 작업을 요청할 수 있는가?
- Pairing Code를 이용해 공식적으로 지원되는 연결을 구축할 수 있는가?

각 항목을 `Supported`, `Experimental`, `Unsupported`, `Unverified`로 분류한다.

### Phase 2. 최소 기능 구현 (MVP)

서버 A와 B에서 실행 중인 Codex 에이전트 간 다음 기능을 구현한다.

```text
Agent B → Agent A: "hello"
Agent A → Agent B: "hello received"
```

이후 다음 기능을 추가한다.

```text
Agent B → Agent A: "현재 작업 디렉터리의 파일 목록을 확인해 줘."
Agent A → Agent B: 파일 목록 반환
```

MVP에서는 실제로 독립적인 두 Codex 세션이 요청을 수신하고 처리했는지 검증해야 한다.

### Phase 3. 파일 전송

서버 B의 요청에 따라 서버 A가 파일을 전송하고 완료 결과를 반환하는 기능을 구현한다.

### Phase 4. 세션 유지 및 안정화

- 기존 대화 세션과 연동
- 에이전트 재연결
- 요청 큐
- 오류 처리
- 동시 작업 관리
- 양방향 요청
- 로그 및 상태 확인

### Phase 5. 사용성 개선

설치와 초기 설정을 가능한 한 간단하게 만든다.

이상적인 사용 흐름은 다음과 같다.

```bash
# 서버 A
codex-bridge start
codex-bridge pair

# 서버 B
codex-bridge connect
```

명령어는 개념적인 목표 인터페이스이며, 실제 구현 과정에서 변경해도 된다.

최종적으로 Codex CLI에 통신 도구가 자동 등록되도록 구성한다.

## 7. 기대 결과물

공개 가능한 Git Repository를 생성할 예정이다.

최소한 다음 내용을 포함한다.

- 실행 가능한 소스 코드
- 설치 및 초기 설정 가이드
- 서버 A/B 연결 방법
- Codex CLI 통합 방법
- 아키텍처 설명
- 네트워크 및 인증 설계
- 기존 세션과의 연동 방식
- 양방향 요청 예제
- 파일 전송 예제
- 테스트 코드
- 보안 관련 주의사항

특정 사용자 환경에 하드코딩하지 않고 다른 Codex 사용자도 활용할 수 있는 범용 프로젝트로 설계한다.

## 8. 첫 번째 작업 지시

지금 당장 전체 시스템을 구현하기보다 다음 순서로 진행해 줘.

1. 현재 설치된 Codex CLI 버전 및 제공 명령어를 확인한다.
2. 공식 문서와 오픈소스 코드를 조사한다.
3. `remote-control start` 및 `pair`의 실제 통신 구조를 분석한다.
4. 공식 Pairing 인프라를 Agent-to-Agent 통신에 활용할 수 있는지 판단한다.
5. 기존 Codex 대화 세션에 외부 요청을 전달하는 방법을 조사한다.
6. 구현 가능한 아키텍처를 2~3가지 제시하고 장단점을 비교한다.
7. 가장 간단하면서 확장성 있는 구조를 추천한다.
8. 검증되지 않은 부분을 명시한 뒤, 우선순위가 높은 최소 PoC부터 구현한다.

**가장 중요한 요구사항은 두 개의 독립적인 Codex 에이전트가 각자의 대화 컨텍스트를 유지하면서 서로 작업을 요청하고 결과를 반환할 수 있어야 한다는 것이다.**

단순한 원격 터미널 제어, 파일 공유, 단일 Codex 세션의 원격 접속만으로 목표를 달성했다고 판단하지 말 것.

기술적으로 불가능하거나 공식적으로 지원되지 않는 부분은 명확하게 보고하고, 목표에 가장 근접한 구현 가능한 대안을 제시해 줘.
